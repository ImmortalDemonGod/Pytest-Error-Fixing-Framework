## Research synthesis

The gathered sources converge on a coherent picture of where this repo — an AI-powered autonomous pytest fixer built as a procedural localize→prompt→apply→verify pipeline — sits relative to the LLM program-repair state of the art, and which upgrades carry the highest leverage. The 2025 survey (arxiv 2506.23749) explicitly places systems like this in the 'procedural pipeline' paradigm and identifies two cross-cutting layers — retrieval augmentation and analysis augmentation — as universal performance boosters; this is the strongest organizing frame for the repo's roadmap. Five themes are corroborated across three or more independent sources.

First, FAULT LOCALIZATION is the highest-ROI gap. Agentless (40.7% Lite / 50.8% Verified), AutoCodeRover (test-based fault localization improved accuracy 16%→20% in ablation), SWE-Fixer (BM25 coarse-to-fine file retrieval), and the leaderboard-profiling analysis (arxiv 2506.17208: hierarchical file→class/function→line localization is universal among high-scorers) all agree that getting the correct file(s) into context is decisive. The repo currently regex-matches each test's error_message to derive an error type but does NOT parse failing tracebacks to localize the responsible source file — closing this is the single most-supported improvement. NOTE A CONTRADICTION the synthesis must respect: the fault-localization-context paper (arxiv 2604.05481) claims line-level context 'frequently degrades performance due to noise amplification,' while the leaderboard-profiling paper reports line-level localization is 'universal among high-scorers.' These can be reconciled — high-scorers use line-level as the FINAL narrowing step on top of already-high-quality file context, not as a substitute for it — but the repo should prioritize file-level localization first and treat line-level as an optional refinement, not a starting point.

Second, MULTI-CANDIDATE SAMPLING WITH TEST-BASED SELECTION beats single-shot retry. Agentless samples multiple patches and validates; SWT-Bench reports an ensemble of four methods solves 71% more samples than the best single method; the leaderboard-profiling paper finds ensemble patch selection common across both agentless and agentic top-tier systems; SWE-Search adds MCTS over candidates for a 23% relative gain. The repo's current flat, temperature-bumping single-candidate retry loop is the weakest-supported design choice and the clearest target for replacement.

Third, CONVERSATIONAL REPAIR WITH STRUCTURED FAILURE INJECTION is validated. ChatRepair (162/337 Defects4J, up to five rounds) and RepairAgent (FSM with info-gathering tools) both confirm that feeding the EXACT failing assertion and buggy lines back — not merely appending raw error text — drives the gains, and that ~5 rounds is a practical empirical ceiling. This directly validates the repo's persistent _messages conversation thread in AIManager and tells it how to refine the feedback payload.

Fourth, AGENT LOOPS WITH CODE-SEARCH TOOLS are the dominant 2024+ paradigm but are NOT strictly required with modern models. SWE-agent's ACI insight, OpenHands (53%→72% with Claude Sonnet 4.5), RepairAgent's three-state FSM, and AutoCodeRover/Moatless's symbol-search APIs all point toward giving the LLM structured code navigation instead of whole-file injection. Crucially, mini-SWE-agent reaching 65%+ on Verified in ~100 lines shows complex scaffolding is now optional — so the repo can adopt retrieval/code-search incrementally without a full agentic rewrite. The existing FixSessionState enum maps cleanly onto RepairAgent's FSM if the team chooses to formalize it.

Fifth, MODEL AND EXECUTION CHOICES ARE WELL-FOUNDED. The leaderboard (Claude Fable 5 95.0%, Opus 4.8 88.6%) and profiling paper confirm the repo's OpenRouter→Claude-family targeting is sound, and OpenHands corroborates Docker-sandboxed per-attempt isolation (already documented as 'not yet implemented' in manager.py) as a worthwhile clean-execution upgrade beyond the current subprocess verify_fix. Finally, benchmark-validity concerns (arxiv 2512.10218: solution leakage, test flaws, OpenAI discontinuing Verified reporting) suggest the SWE-bench framing should be held loosely — the repo's actual-test-re-run verification is arguably more rigorous than leaderboard pass rates imply, and aspirational comparisons should target SWE-bench Pro rather than the contaminated Verified set.

Low-relevance / dropped: SWE-RL (RL fine-tuning of Llama on software evolution) is interesting but inapplicable to a tool that consumes hosted models via OpenRouter and does no training; it is retained only as context.

Multiple independent SWE-bench systems show file-level localization is the dominant accuracy driver; AutoCodeRover's ablation isolates a +4pp gain from test-based fault localization specifically. ### Unverified claims (single/weak source)

- Moatless Tools' claim of 'competitive SWE-bench results with Claude 3.5 Sonnet and GPT-4o' rests on a single self-reported GitHub source (marked corroborated:false); the underlying symbol-navigation concept is corroborated by AutoCodeRover, but these specific benchmark results are not independently confirmed.
- The fault-localization-context paper's specific quantitative claims (file-level localization yields 15-17x improvement; line-level context 'frequently degrades performance'; 61 configurations over 798 bugs; arxiv 2604.05481) are single-sourced (corroborated:false) and the line-level-degrades claim directly CONTRADICTS the leaderboard-profiling finding that line-level localization is universal among high-scorers. The directional message (file-level is most important) is well-corroborated; the magnitudes and the line-level penalty are not.
- Benchmark-contamination specifics (30%+ of successful SWE-bench Verified passes involve solution leakage; 59.4% of o3 failures were test flaws; SWE-bench Pro recommended) come from a single source (arxiv 2512.10218) and have not been cross-confirmed here.
- The SWE-RL claim (Llama 3-70B RL on software evolution reaching 41.0% on Verified) is single-sourced and its relevance summary is truncated in the gathered data; it is also low-relevance to a hosted-model OpenRouter tool that does no training, so it was not promoted to a key idea.
