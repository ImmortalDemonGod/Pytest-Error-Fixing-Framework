# Bug catalog — pef-p11-remove-dev-force-success-byp

- **Silent fix-pipeline bypass via `dev_force_success`.** `src/branch_fixer/orchestration/fix_service.py:116-122` (`FixService.attempt_fix`): when `self.dev_force_success` is `True`, the method calls `error.mark_fixed(attempt)` and returns `True` immediately, **without ever calling `self.ai_manager.generate_fix(...)`**, without applying any code change, and without running `_verify_fix`. Wrong: a test is reported "fixed" with zero AI generation, zero patch application, and zero verification. Correct: `attempt_fix` must unconditionally call `ai_manager.generate_fix`, apply the change, and verify it — there must be no code path that marks an error fixed without going through AI generation.

- **`dev_force_success` still threaded from CLI config into `FixService`.** `src/branch_fixer/utils/cli.py:325` (`CLI.setup_components`): `FixService(..., dev_force_success=config.dev_force_success, ...)` wires the CLI's `ComponentSettings.dev_force_success` flag straight into the constructor that enables the bypass above. Wrong: any caller who sets `dev_force_success=True` on `ComponentSettings` (including a stray/legacy default) can silently disable the entire AI-fix pipeline. Correct (PRD Phase 2, audit/02-static-audit.md L24): the flag must be removed — `FixService` must always call the AI service, so `setup_components` must not pass `dev_force_success` at all.

- **`dev_force_success` also repurposed to control interactive mode.** `src/branch_fixer/utils/cli.py:347`: `FixOrchestrator(..., interactive=not config.dev_force_success)`. Wrong: `dev_force_success` conflates two unrelated concerns (skip AI generation vs. suppress interactive prompts), so setting it True to get non-interactive behavior also silently activates the fix-bypass above. Correct: interactivity should be driven solely by the CLI's explicit `--non-interactive` flag, independent of any force-success mechanism (which should not exist).

- **`ComponentSettings.dev_force_success` field itself.** `src/branch_fixer/utils/cli.py:39` (`ComponentSettings` dataclass): exposes `dev_force_success: bool = False` as a first-class, user-settable CLI config field (`--dev-force-success` per PRD). Wrong: keeping this field/flag on the public config surface preserves the bypass entry point even if downstream wiring were tightened. Correct: the field and its corresponding CLI option must be removed entirely so `fix --help` no longer advertises a way to skip AI-based fixing.
