# Bug catalog — pef-p15-align-push-merge-return-sema

- **push() silently swallows GitError instead of raising it (F78).** `src/branch_fixer/services/git/repository.py:314` — the docstring declares `Raises: GitError: If the push operation fails.` But the whole method body is wrapped in `except Exception as e: logger.error(...); return False` (`repository.py:333-335`), which also catches the `GitError` that `run_command()` raises on a failed `git push`. Wrong: `push()` returns `False` on a real push failure. Correct: `push()` should let `GitError` propagate (or re-raise it), matching its own documented contract.

- **push()'s `success`/`else` branch is dead code (F67).** `src/branch_fixer/services/git/repository.py:325-329` — `success = result.returncode == 0` followed by an `else: logger.error(...)` branch. Since `run_command()` (`repository.py:193`, `_check_command_error`) already raises `GitError` for any non-zero return code, `result.returncode` can never be non-zero by the time line 325 executes. Wrong: the failure-logging `else` branch (line 329) is permanently unreachable with a real subprocess. Correct: failure should be detected and reported via the propagated `GitError`, not via a `returncode == 0` check that can never be false.

- **merge_branch()'s declared `bool` failure return is dead code (F69).** `src/branch_fixer/services/git/repository.py:612` — `return result.returncode == 0`. Because `run_command()` already raises `GitError` on any non-zero return code, this expression is always `True` when reached; `merge_branch()` never actually returns `False` on failure — it either returns `True` or has already raised. Wrong: the method's `-> bool` signature and docstring ("Returns: bool: True if merge was successful, False otherwise") imply a `False` return path that cannot occur. Correct: a failing merge should visibly surface as a raised `GitError`, not be modeled as a reachable `False` return.
